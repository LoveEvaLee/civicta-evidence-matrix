# 실습 2차: 각자 PR 2건 이상 만드는 고도화 백로그

> 아래는 작업 배정을 위한 **제안 이슈**입니다. GitHub Issues·PR이 실제 만들어진 것은 아닙니다. 각자 실제로 실행·확인하고 PR에 증거를 남깁니다.

## A / 과학기술정책 담당

### Issue A-1 · CSV 입력 검증 기능 보완
- 파일: `docs/js/import.js`, `docs/js/normalize.js`, `tests/test.js`
- 작업: 동일 DOI 발견 시 중복 건수 표시; 누락 DOI와 형식 오류 분리; 예시 CSV 재입력 검산 기록.
- 완료: 이상 사례 3개를 재현하고 수정 전후 결과 비교. 실제 웹 화면 확인.

### Issue A-2 · 정책 반영 근거 코드북 개정
- 파일: `docs/rules.js`, `planning/기획안.md`
- 작업: `반영 근거 확인`과 `반영 주장·근거 불명`을 구분하는 근거 판정 문장 보완. 단순 보고서 전달은 반영 확정으로 보지 않음.
- 완료: 가상 예시 2건 판정 근거 설명. 팀원 리뷰·동의 후 병합.

## B / HCI 담당

### Issue B-1 · 접근성/상호작용 개선
- 파일: `docs/index.html`, `docs/styles.css`, `docs/js/app.js` (공동 파일 수정 범위 먼저 합의)
- 작업: 키보드 탐색과 셀별 상세 패널의 사용성 개선, 모바일 레이아웃 검증.
- 완료: 마우스 없이 셀 선택 및 문헌 목록 확인 가능, 시연 영상.

### Issue B-2 · 결과물 정책연구 재사용성 개선
- 파일: `docs/js/export.js`, `tests/test.js`
- 작업: Markdown 결과에 적용 코드북 버전·미분류 이유·분석 범위 고지 추가.
- 완료: 내보낸 Markdown 내용과 화면의 집계 숫자·문헌 수 일치.

## PR 리뷰 작성 예시

```markdown
Refs #<실제 이슈 번호>  (완료 조건 확인 뒤 이슈를 직접 닫음)

### 에이전트가 한 일
- 무엇을 자동 생성/수정했는지와 변경된 파일

### 사람이 판단한 지점
- 어떤 정책·HCI 분류 규칙을 왜 채택했는지

### 확인한 방법
- 입력 파일: data/demo-literature.csv
- 기대 결과: 12건, 모든 셀의 합 12
- 추가 검사: 미분류, 중복 DOI, 내보내기 재입력
- 확인하지 못한 것: 실존 논문의 내용분류 / 외부 DOI 자동조회
```

## 충돌 실습 시나리오

A와 B가 **같은 출발 커밋**에서 `docs/rules.js`의 `codingProtocol` 목록 맨 끝에 각자 한 줄을 더합니다(문구는 기획안 2차 참고).
A의 PR을 먼저 병합한 다음 B의 PR에서 충돌이 발생하면, 정책 반영 기준과 HCI 반영 기준이 논리적으로 양립하는지 논의하고 둘 다 살린 최종 규칙을 남깁니다.
충돌 표시만 지운다고 완료가 아닙니다. **A/B 최종 문구가 둘 다 남아 있고 테스트가 통과하는지** 다시 실행합니다.

## GitHub 실제 프로세스

1. 담당 Issue 등록 → 자신의 `feat/` 브랜치 생성.
2. 맡은 파일만 수정 → 직접 실행 → `git commit` → `git push`.
3. PR 본문 3칸과 `Refs #번호` 연결(완료 조건 확인 뒤 이슈를 직접 닫음).
4. 상대가 실제 CSV로 검산 후 **Review changes → Approve** 또는 **Request changes**.
5. 승인 후 소유자·협업자가 병합; Issues 종료 확인.
6. 팀원 fork `Sync fork` (개인 중간과제 기간에는 금지).
